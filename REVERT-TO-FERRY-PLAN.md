# Plan: Revert to Pure Ferry Architecture

**Status:** 📋 PLANNED - Not yet executed
**Created:** 2025-11-16
**Priority:** HIGH - Architectural alignment

## Executive Summary

Remove MCP-specific delegation tools from the bridge to restore the original "pure ferry" architecture where the bridge has NO knowledge of specific MCPs (HubSpot, Asana, SharePoint, etc.).

## Problem Statement

The current implementation violates the bridge's core design principle:

**Current (Problematic):**
- Bridge has 4 MCP-specific tools: `delegate_hubspot_task`, `delegate_asana_task`, `delegate_sharepoint_task`, `delegate_batch_tasks`
- Bridge "knows" about specific MCPs via hardcoded tools and config
- Adding new MCPs requires code changes, rebuilding, and republishing
- Defeats the token-saving purpose (each MCP adds tools to Desktop's context)
- Creates coupling between bridge and MCP implementations

**Target (Pure Ferry):**
- Bridge has only 4 generic tools that work with ANY MCP
- MCP configuration is passed **by the caller**, not generated by bridge
- Bridge is completely MCP-agnostic - it just ferries messages
- No code changes needed when adding new MCPs
- Zero coupling to MCP implementations

## Architectural Vision

### Original Design Intent
The bridge should be a **transparent message conduit**:

```
Desktop → Bridge → Code subprocess
         (ferry)   (with any MCP config)
```

The bridge should:
- Accept generic execution requests
- Pass MCP configurations transparently
- Return results
- **Never know or care which MCPs exist**

### How It Will Work After Revert

**Caller provides MCP config:**
```typescript
execute_task({
  prompt: "Search Asana for tasks assigned to Butch",
  mcpConfigPath: "/tmp/my-asana-config.json"  // Caller manages this!
})
```

**Bridge simply:**
1. Accepts the request
2. Spawns Code with `--mcp-config /tmp/my-asana-config.json`
3. Returns results
4. Never inspects or knows what's in the config

## What Remains After Revert

### 4 Generic Tools (MCP-Agnostic)

1. **execute_task**
   - Execute any prompt with optional MCP config
   - Parameters:
     - `prompt` (required): Task to execute
     - `mcpConfigPath` (optional): Path to MCP config file (caller provides)
     - `timeout` (optional): Timeout in ms
     - `permissionMode` (optional): Permission mode

2. **execute_with_tools**
   - Execute with specific allowed tools
   - Parameters:
     - `prompt` (required)
     - `allowedTools` (required): Array of tool names
     - `mcpConfigPath` (optional)
     - `timeout` (optional)

3. **execute_with_permission_mode**
   - Execute with specific permission mode
   - Parameters:
     - `prompt` (required)
     - `permissionMode` (required): plan | acceptEdits | default | bypassPermissions
     - `mcpConfigPath` (optional)
     - `timeout` (optional)

4. **get_session_info**
   - Get information about a session
   - Parameters:
     - `sessionId` (required): Session ID to query

### Core Capabilities Retained

- ✅ Spawn Code subprocesses
- ✅ Pass MCP configs to Code (caller provides path)
- ✅ Capture streaming JSON output
- ✅ Session management
- ✅ Event emission
- ✅ Diagnostics and logging
- ✅ Timeout handling
- ✅ Permission mode control
- ✅ Tool filtering

## Migration Guide for Users

### If You Were Using Delegation Tools

**Before (v1.x):**
```typescript
// Desktop calls the bridge's delegation tool
delegate_asana_task({
  prompt: "Search for tasks assigned to Butch"
})
```

**After (v2.0):**
```typescript
// Caller creates MCP config first
const configPath = "/tmp/my-asana-config.json";
writeFileSync(configPath, JSON.stringify({
  mcpServers: {
    asana: {
      type: "sse",
      url: "https://asana-mcp-railway-production.up.railway.app"
    }
  }
}));

// Then calls generic execute_task
execute_task({
  prompt: "Search for tasks assigned to Butch",
  mcpConfigPath: configPath
})
```

### Desktop Config Changes

**Before:** Desktop had `claude-code-bridge` with delegation tools
**After:** Desktop can either:
1. Call bridge's execute_task with MCP configs it manages
2. OR use MCPs directly (if Desktop supports them)

The bridge no longer manages MCP configurations.

## Alternative Approaches Considered

### Alternative 1: Keep Delegation, Make Dynamic
Add a single `delegate_to_mcp` tool with dynamic enum.

**Rejected because:**
- Bridge still needs to know about MCPs
- Still requires config system
- Doesn't solve the coupling problem
- Only reduces from 4 tools to 1 (marginal improvement)

### Alternative 2: Hybrid Approach
Keep both ferry tools AND delegation tools.

**Rejected because:**
- Increases complexity
- Confusing to users (which tools to use?)
- Maintains the architectural conflict
- Doesn't solve token overhead problem

### Alternative 3: Pure Ferry (SELECTED)
Remove all MCP-specific code.

**Selected because:**
- Aligns with original vision
- Simplest possible design
- Maximal flexibility
- Minimal token overhead
- Clearest separation of concerns
